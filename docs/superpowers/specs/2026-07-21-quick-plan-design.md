# Quick Plan — Single-Location Itinerary Generator

**Date:** 2026-07-21
**Status:** Approved (user-refined)

## Problem

Quick Plan is for users who already know where they want to go. Instead of planning a meetup from multiple member locations, the planner generates several complete itineraries centred around a single chosen area or venue, using the same planning engine as the group planner. Every suggested stop stays within that selected locality.

## Goals

- Reuse `executePlanningEngine`. **All stage logic unchanged** — archetypes, constraint stack, scoring, clustering, budget×1.10 ceiling. Two *additive optional* params (`planningArea`, `requiredVenueId`) that group flow never passes.
- **Every suggested stop stays within the selected locality** — all slots of all plans drawn from one area around the target point.
- Three location modes: area, exact map location, specific place.
- Logged-in, save-per-plan to existing `history` table.
- Reuse planner rate limit (admin emails bypass).

## Non-Goals

- No group creation, invites, member detail collection.
- No new scoring/generator (would fork planner logic → drift). Rejected.
- No throwaway group rows in D1 (pollution + cleanup burden). Rejected.
- No "quick mode" conditionals sprinkled through planner stages — the synthetic group makes every downstream stage behave naturally.

## Planning Area (core requirement)

Engine mechanic (verified): `selectCandidateZones(memberCoords)` picks **4 spaced-out zones** near the centroid; each zone fetches venues within **6km of its center** (`radiusKm=6.0`); candidates generated by sweeping **template × zone × budget-tier**; clustering picks 4 distinct plans spread across those zones.

To keep everything in one locality: **feed exactly one candidate zone = the target point.** All candidates draw from that single area; clustering still returns 4 distinct plans (different archetypes + budget tiers) — every venue inside the locality.

**Additive engine params** (describe the feature, not the mechanism):
```
executePlanningEngine(..., options, planningArea?, requiredVenueId?)
planningArea?: { lat: number; lng: number; name: string; radiusKm: number }
```
- `planningArea` set → skip the 4-zone selection block, `candidateZones = [planningArea]`, venue fetch uses its `radiusKm`. Absent → existing behavior byte-for-byte.
- `requiredVenueId` set → **a candidate plan is invalid unless that venue appears in it.** Enforced during candidate generation (not injected afterwards), so scoring, travel calculations, and archetypes stay consistent — plans are generated *around* the mandatory venue.
- Thread both through exported `executePlanningEngineForEval`.

**Radius is an implementation detail** — never exposed to the caller or UI. The service decides by mode:

| Mode | Radius |
|------|--------|
| Area (zone) | 6 km |
| Exact map location (pin) | 3.5 km |
| Specific place (venue) | 2.5 km |

## Preflight Viability Check

Before running the engine, the service checks the area can actually support itineraries **at the requested time** (10:30 PM in Bandra ≠ 10:30 AM in Bandra):

```
planningArea → fetch nearby venues (existing by-zone path)
            → filter by isVenueOpenAtTime(category, outingTime)   [existing helper]
            → count < MIN_VIABLE (12) → friendly error, no engine run
            → else → planner
```

Saves full planner execution on hopeless inputs; user gets "Not enough open venues near {name} at {time}. Try a wider area, different time, or nearby landmark."

## Approach: Synthetic-Group Adapter

Engine takes plain args: `groupData, presentMembers, budgetSummary, presentLocations, preferredCategories, vibes, historyEntries, lowestBudget, options`. Fabricate:

- N members (headcount clones)
- identical coordinates (the chosen point)
- normalized budget (per-person as-is; total ÷ headcount)
- mapped categories (tags → preferredCategories, tags ∩ vibeVocab → vibes)

Every downstream stage behaves naturally. Nothing persisted until the user saves.

## Data Flow

```
/quick-plan form
  → generateQuickPlanAction(input)         [server action, auth + rate-limit]
    → quickPlanService.generate(input)
        1. resolve location by mode → planningArea { lat, lng, name, radiusKm } (+ requiredVenueId for place mode)
        2. preflight viability check (open venues at outing time ≥ MIN_VIABLE)
        3. synthesize groupData / presentMembers / presentLocations / budgetSummary / categories / vibes
        4. executePlanningEngine(..., options, planningArea, requiredVenueId)  ← stage logic UNCHANGED
        5. return 4 PlanWithSlots (in-memory) — all venues within planningArea
  → results grid → Save button per plan | Generate Again
    → saveQuickPlanAction(plan, request)
      → worker POST /internal/quick-plan/save → history row (groupId NULL, source='QUICK', metadata=request JSON)
```

## Location Mode Resolution

| Mode | Input | Resolves to |
|------|-------|-------------|
| Area | zone name (Bandra) | `planningArea` = zone center, 6 km |
| Exact map location | address / map pin | geocode via existing maps lib → 3.5 km |
| Specific place | must-visit place | venue coords (places DB / geocode) → 2.5 km + `requiredVenueId` |

Geocoding + venue lookup reuse existing maps/places helpers. No new external call types.

## Regeneration

"Generate Again" must not return identical plans. The engine already shuffles candidate combos and zone order per run (`Math.random` in combo shuffle + jitter), so a fresh call naturally explores different combinations under the same constraints. Quick-plan **bypasses the itinerary cache** (no cache key written for synthetic groups) so every generation is a fresh engine run. UI offers Generate Again with same inputs.

## Persistence (existing history table)

- Reuse `history`. `groupId` nullable, `source` column: `'GROUP'` (default, existing rows) | `'QUICK'`. Keeps future analytics (quick-plan usage %, save rate, feedback score, conversion to group planning) in one table.
- **`metadata` column stores the original request** — e.g. `{"location":"Bandra","mode":"ZONE","budget":1000,"perPerson":true,"headcount":2,"tags":["food","date"]}` — the exact prompt that generated the itinerary.
- Migration `0021_quick_plan_history.sql`: `ALTER TABLE history ADD COLUMN source TEXT DEFAULT 'GROUP'; ALTER TABLE history ADD COLUMN metadata TEXT;` + make group_id nullable if needed (verify; SQLite ALTER can't change nullability — history.group_id may already allow null or needs workaround: write `''` sentinel if NOT NULL).
- Save-per-plan → worker `POST /internal/quick-plan/save` writes one history row shaped like group history so `/users/history`, share links, and post-outing feedback work unchanged.

## Rate Limiting

Reuse planner's per-user daily generation limit (same cost-control endpoints). Admin emails bypass. Action passes `{ clerkId, ip, email }`.

## Error Handling

- Out-of-region coords → same `validateCoordinates` reject as planner.
- Geocode failure → "couldn't find that location, try a nearby landmark".
- Preflight fail → "not enough open venues near X at that time".
- No plans within budget → same `ValidationError` as planner.
- Rate limit → same 429 path.
- Save failure → toast, results stay on screen.

## Testing

- Unit: tag→category mapping, budget normalization, mode resolvers, preflight threshold.
- Integration: all 3 modes → 4 valid plans, all venues within radius, requiredVenueId present in every plan (place mode), budget×1.10 respected.
- Manual: form → generate → regenerate differs → save → history shows QUICK row with metadata → share + feedback work.

## Open Risks

- **Thin catalog in a tight radius.** Preflight catches the worst; engine fallback-pad fills the rest. Never widen radius silently — that breaks the locality guarantee.
- **requiredVenueId vs archetype fit.** If no archetype can seat the venue's category, all candidates fail → surface "couldn't build a full outing around that place, try Area mode". Verify behavior during impl.
- Synthetic `groupData` must include every field the engine reads (outingDate, outingTime, groupType, vibes, generationOptions, activity, outingType, outingIntent, requiredPreferences). Default any missing.
