# Quick Plan — Single-Location Itinerary Generator

**Date:** 2026-07-21
**Status:** Design (pending user approval)

## Problem

Group planner requires: create group → invite members → collect each member's location/budget/vibes → admin generates. Heavy for a user who already knows where they want to go and just wants itinerary ideas for that spot.

**Quick Plan** = single user, one known location + direct params (headcount, budget, tags) → 4 itineraries from the same engine → save favorite to history.

## Goals

- Reuse `executePlanningEngine`. **All stage logic unchanged** — archetypes, constraint stack, scoring, clustering, budget×1.10 ceiling. Only one *additive optional* param (`lockLocation`) that group flow never passes.
- **All suggested venues in the chosen location only** — every slot of every plan drawn from one ~6km area around the target point.
- Three location modes: anchor zone, exact point, single must-visit venue.
- Logged-in, save-per-plan to existing `history` table.
- Reuse planner rate limit (admin emails bypass).

## Non-Goals

- No group creation, invites, member detail collection.
- No new scoring/generator (would fork planner logic → drift). Rejected.
- No throwaway group rows in D1 (pollution + cleanup burden). Rejected.

## Location Lock (core requirement)

Engine mechanic (verified): `selectCandidateZones(memberCoords)` picks **4 spaced-out zones** near the centroid (lines 3562-3606); each zone fetches venues within **6km of its center** (line 3677, `radiusKm=6.0`); candidates generated by sweeping **template × zone × budget-tier** (line 4237); clustering picks 4 distinct plans spread across those zones. This is why default group plans span multiple areas.

To keep everything in one location: **feed exactly one candidate zone = the target point.** Every combo then uses `zoneIdx=0`, all 40 candidates draw from that single 6km area, and clustering still returns 4 distinct plans (different archetypes + budget tiers) — but **every venue sits in that one location.**

**Additive engine change** (not a stage-logic edit): new optional last param
```
executePlanningEngine(..., options, lockLocation?)
lockLocation?: { lat: number; lng: number; name: string; radiusKm?: number }
```
When `lockLocation` is set, skip the 4-zone selection block (3562-3606) and set `candidateZones = [{ name, lat, lng }]` with the zone's `radiusKm` override (default 6, form may narrow to e.g. 3km for a tighter "in this spot only" feel). When absent → existing behavior byte-for-byte (group flow passes nothing). Archetypes/scoring/clustering/ceiling all execute identically, just over one zone. Also thread through the exported `executePlanningEngineForEval` wrapper.

## Approach: Synthetic-Group Adapter

Engine takes plain args (verified line 3549): `groupData, presentMembers, budgetSummary, presentLocations, preferredCategories, vibes, historyEntries, lowestBudget, options`. Derives everything from `memberCoords = presentLocations.map(lat/lng)`. No DB handle, no module-scope group state.

New `quickPlan.service.ts` synthesizes those args from quick-plan input and calls the engine directly. Nothing persisted until the user saves.

## Data Flow

```
/quick-plan form
  → generateQuickPlanAction(input)         [server action, auth + rate-limit]
    → quickPlanService.generate(input)
        1. resolve location by mode → { lat, lng, locationName, meetupZone?, anchorVenueId? }
        2. synthesize:
             groupData      = { id:`quick_<uuid>`, name, groupType, outingDate, outingTime, vibes, ... }  (in-memory, no row)
             presentMembers = headcount clones [{ userId, clerkId, ... }]
             presentLocations = [{ userId, lat, lng, locationName }]   // one point; all members share it
             budgetSummary  = { min, avg, max } from budget (perPerson → as-is; total → /headcount)
             preferredCategories = mapTagsToCategories(tags)
             vibes = tags∩vibeVocab
             lockLocation = { lat, lng, name, radiusKm }               // forces single-zone venue fetch
        3. executePlanningEngine(..., options, lockLocation)  ← stage logic UNCHANGED, one additive param
        4. return 4 PlanWithSlots (in-memory) — all venues within lockLocation radius
  → results grid (reuse plan card) → Save button per plan
    → saveQuickPlanAction(plan)
      → worker POST /internal/quick-plan/save  → history row (groupId NULL, source='QUICK')
```

## Location Mode Resolution

All three modes resolve to one `lockLocation { lat, lng, name }` — every plan's venues stay within its radius.

| Mode | Input | Resolves to |
|------|-------|-------------|
| Anchor zone | zone name (Bandra) | `lockLocation` = zone center coords, name = zone |
| Exact point | address / map pin | geocode via existing maps lib → `lockLocation` = that lat/lng |
| Single venue | must-visit place | venue coords (places DB / geocode) → `lockLocation` = venue point; `anchorVenueId` seeded into first slot / `usedPlaceIds` so that venue is guaranteed in the plan, rest of crawl fills around it within radius |

Geocoding + venue lookup reuse existing `src/lib/maps/places` helpers. No new external calls beyond what planner already makes.

## Persistence (existing history table)

- Reuse `history`. `groupId` nullable, new `source` value `'QUICK'` (existing rows implicitly `'GROUP'`).
- Migration `0021_quick_plan_source.sql`: `ALTER TABLE history ADD COLUMN source TEXT DEFAULT 'GROUP';` — remote D1 + local.db + schema.ts. (Only if `source` column absent; verify first.)
- Save-per-plan: user picks 1 of 4 → `saveQuickPlanAction` → worker `POST /internal/quick-plan/save` writes one history row (venues_json, participants_json synthesized, total_cost_per_head, etc — same shape as group history so `/users/history` + share + feedback all work).
- Quick plans appear in existing history list; share link (#66) + post-outing feedback (#67) work unchanged since they key off history rows.

## Error Handling

- Invalid/out-of-region coords → same `validateCoordinates` reject as planner ("outside supported Mumbai/Navi Mumbai/Thane region").
- Geocode failure → surface "couldn't find that location, try a nearby landmark".
- No plans within budget → same `ValidationError` as planner ("raise budget or adjust preferences").
- Rate limit hit → same 429 path as planner.
- Save failure → toast, keep results on screen (not lost).

## Open Risks

- **Thin catalog in a tiny radius.** A narrow radius over a sparse area may yield <4 distinct plans (or fewer slots). Mitigation: default radius 6km (same as group), let the engine's existing fallback-pad path fill; if still short, surface "few venues near there, try a wider area or nearby landmark." Never widen silently past the lock — that would break the guarantee.
- **Single-venue anchor + category clash.** Anchored venue's category may not fit any archetype's first slot. Mitigation: seed into `usedPlaceIds` and let scoring place it; if it can't be placed, keep it as guaranteed slot 1 and build the rest around it. Verify during impl.
- Synthetic `groupData` must include every field the engine reads (outingDate, outingTime, groupType, vibes, generationOptions, activity, outingType, outingIntent, requiredPreferences). Enumerate from engine + `buildFallbackItineraryData` reads during impl; default any missing.
